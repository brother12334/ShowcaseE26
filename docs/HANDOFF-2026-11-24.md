## The project

- `/index.html` — the entire app. ~76,000 lines: markup, one `<style>`, one `<script>`.
  No build step, no framework, `"use strict"`.
- `sw.js` — service worker. Its `VERSION` string must match `APP_VERSION`.
- `glass/` — the dark-glass design package: `tokens.css`, `glass.css`, `glass-config.js`
  (motion numbers), `layout.js` (per-screen shape placement), `scene.js`, `intro.js`.
  **These are the designer's files. Do not redraw glass in CSS, SVG, canvas or WebGL.
  Use the shipped art as it is.**
- `assets/` — baked art. `heroes/*.webp` (stills, 780×1280), `hero-video/*.mp4`
  (780×1280, 30fps, ~3.7s), `hero-overlays/*`, `shapes/*`.
- `tests/specs/*.mjs` — 335 Playwright specs. `node tests/run.js` runs all of them and
  takes about 25 minutes.
- `docs/` — notes. `HANDOFF-dark-glass.md` is the previous handoff and still useful.
- Repo `brother12334/ShowcaseE26`, published at https://brother12334.github.io

## Rules the owner has set. These are not suggestions.

1. **Every change goes to BOTH branches**: `main` and
   `claude/element26-pdf-importer-timl9t`.
2. **Version bump on every app release.** `APP_VERSION` and `NEWS_FOR` in `index.html`,
   `VERSION` in `sw.js`. Format `YYYY.MM.DD.N`. **Never reuse a string, never go
   backwards.** `NEWS_FOR` must always equal `APP_VERSION`, and bumping it means
   **adding a `NEWS` entry** (newest first, at the top of the `NEWS` array).
   Test-only and comment-only changes need no bump.
3. **Every change is verified by a Playwright spec plus the full suite before pushing.**
   Not after. The suite has caught a real regression on most runs in this project.
4. **Every spec carries a control that must fire** — an assertion that proves the test
   was looking at something. A spec that passes against an empty page is worthless, and
   this suite has had several.
5. **If you change an assertion instead of the code, say in the commit message why the
   old expectation was wrong.** This is the owner's rule and it is the most important
   one. Loosening a spec to make a change go green is the failure mode it exists to
   stop.
6. **One commit per feature.** If your change to screen A needs a style change to a
   class that feature B owns, that is its own commit, written in B's own stylesheet
   section.
7. Current version: **2026.11.24.12**. Suite: **335 specs, all passing** as of the last
   full run. Check `git log --oneline -15` for recent history; the commit messages are
   detailed on purpose and are the best record of why things are the way they are.

## What the work is

A redesign to the "dark glass" look. The design package ships a PNG mockup per screen in
`element26-dark-glass/mockups/`: `today`, `today-rest-day`, `workout`, `history`,
`program`, `research`, `research-paper`, `body`, `settings`, `settings-rest-timer`.
**A screen is finished when it looks like its mockup, not when its hero works.**

Hard limits from the design brief, all currently satisfied:
- at most 6 shapes per screen, at most 3 spinning (currently 0 spin anywhere)
- nothing in the bottom 110px
- shapes are `pointer-events:none` and `aria-hidden`
- hero videos `muted playsinline`, paused off-screen
- text over glass keeps 4.5:1; **if a shape sits on text, move the shape**
- `prefers-reduced-motion` respected
- all real content stays real text

## Traps. Read these; every one of them cost real time.

**The em-dash trap.** The file mixes literal `—`, `→`, `·` with their escape text. If
you patch by string match, check which form the line actually contains or your anchor
will not match. `sed -n 'N,Mp' index.html | cat -A` tells you.

**`cssdupe`.** `tests/specs/cssdupe.mjs` forbids one class being defined in two banner
sections of the stylesheet. A banner is a comment opening with a run of dashes or equals
signs. So an override for another feature's class must be written **in that feature's own
section**, and it must not introduce a foreign class into that section — scope it with an
attribute instead. `[data-dg-screen="program"] .pv-r { … }` is fine;
`.dg-screen .pv-r { … }` is a crossing, because `.dg-screen` belongs to the dark-glass
section.

**A closed `<details>` is not in `innerText`.** Today keeps its notices behind one fold
now. Three separate specs reported features as *missing* when they were one tap away.
Any spec that reads text off Today must open the folds first.

**`oldBuild()` used to cache by the ref's name.** It wrote `tests/.old/HEAD~1.html` and
reused it whenever any spec asked for `HEAD~1`, so after the next commit, every
"nothing went missing" guard in the suite was reading a file from whenever it was first
written. Fixed — it caches by resolved sha now. Do not reintroduce a name-keyed cache,
and do not write a control that compares against "the previous build" for a change that
is itself about to become the previous build.

**`boot()` in a spec plants state and then calls `applySplit()`**, which rebuilds the
cycle and clears what you planted. If what you are testing depends on `S.cycleDone`,
`S.pointer` or similar, mutate *after* boot and call `render()` yourself.

**`bodyLogDue("weight")` returns an object, not a boolean.** `!!bodyLogDue("weight")` is
always true. Read `.due`.

**Today builds its own wrapper.** It does not go through `dgScreenHTML()`. Both of its
branches now carry `class="dg dg-screen"` and `data-dg-screen="today"` or `"rest"`; if
you add a screen, give it the attribute or none of the shared rules will reach it.

**Specificity on `.btn`.** `.btn.danger` sets only a colour. A `.dg-screen .btn` rule
that sets `color` is equally specific and later in the file, so it silently repainted
twenty-two "Delete session" buttons as ordinary ones. `dangerbtn.mjs` catches it.

**Measure before you theorise about performance.** The owner reported stuttering shapes
for days. The shapes were not the cause — Today has none in its layout. Cropping the
hero out of a screen recording and taking the per-frame pixel difference showed the
picture changing once every four captured frames, in a perfectly regular cadence:
`0.0 0.0 0.0 3.8` repeating, about 15 updates a second, nothing dropped. It was
`heroRate: 0.5`, set as a performance fix, halving how often the picture changed. The
phone was never struggling. `ffmpeg -vf "crop=…,scale=120:140,format=gray" -f rawvideo`
and a few lines of Python is the whole technique; it is worth more than any amount of
reasoning about compositing.

**Do not trust a verification tool you have not checked.** A headless rAF timing probe
in this project reported a flat 16.7ms for every variant and was worthless. A
byte-identical comparison of a rebuilt component against the old one caught a real break
on its first run. Prefer the second kind.

## How to work

- Read the mockup, screenshot the live screen at 390px wide, and compare them directly.
  A screenshot harness that serves the repo over HTTP and seeds a fixture is the only
  way to see the real screen; `file://` cannot fetch the glass package and the tab falls
  back to an error panel.
- Fixtures live in `tests/fixtures/`. `state-2026-11-17.json` is the main one.
- When something must differ from its mockup — and several things must — say so in the
  commit message with the reason, and add a spec that guards the deviation. Two on the
  rest day: tomorrow keeps its list of movements where the mockup draws a count, and
  there is no standing offer to train on a rest day. Both are in `dgrest.mjs`.
- The owner reads commit messages. Write them like you are explaining the decision to
  the person who will ask why in six months, because that is what they are for.
